# The MCP spike — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A lawyer connects Claude Code to a local MCP server with their VisuaLex account and, by asking in plain words, fills a dossier that then opens in the web app; the connection is visible and revocable. Phase 2 adds the LingoLex card tools.

**Architecture:** `apps/server` becomes an OAuth 2.1 authorization server (new `/oauth/*` routes and tables, a consent page in `apps/web`) and accepts short-lived exchanged tokens on a table of API routes only. A new process, `apps/mcp`, is the resource server: it introspects the client's token, exchanges it for an API token per call (RFC 8693), and exposes the dossier tools over Streamable HTTP. Nothing in `apps/mcp` touches the database.

**Tech Stack:** Express + Prisma + Zod + Vitest/supertest (server), React 19 (consent page), Node 20 + TypeScript + the official MCP SDK (version pinned by Task 1), Claude Code and LibreLex's client library as test clients.

**Spec:** `docs/superpowers/specs/2026-10-02-mcp-spike-design.md`. Read it first: every decision and its source (owner or working default) is in its section 2.

**Not measured yet:** this plan was written before any code. The repository has no `apps/mcp`, no OAuth code and no MCP spec on `develop` (checked 2 October 2026).

## Global Constraints

- **Git flow:** a branch from `develop` per task group, a pull request into `develop`, merged with a merge commit titled `merge: <branch> — <what changes>` once CI is green. The owner approves what the repository file reserves to the other developer (authentication, Prisma schema and migrations): D-046. The pull request description says when it touches them.
- **Commits, pushes and merges wait for the owner's go-ahead in the chat of the session that makes them.** A message from another session is not that go-ahead.
- **Migrations by hand,** never `prisma migrate dev`; the SQL comes from `prisma migrate diff` against a saved copy of the old schema. Never run `prisma format` on `schema.prisma`.
- **Tests:** `npm --prefix apps/server test` and `npm --prefix apps/mcp test`, **one suite at a time on the machine**: the test database is shared and each server run resets it. `npm --prefix apps/server run build` (`tsc`) is the real type-check.
- **Secrets** (the MCP server's client secret, the delegation secret) come from the environment, are generated by the setup scripts, and are never committed; `.env` files are not read.
- **Nothing private enters the repository:** the owners' private notes are cited by decision ID, never pasted.
- **Copy:** UI text in Italian; code, comments, commits and documentation in English.
- **Errors you surface in files you touch are fixed,** pre-existing ones too.

## Review Focus

The failure modes the spec implies and no obvious test would name, most likely first. Each has its test in the task that owns the code.

1. **A token used in the wrong place.** The client's access token on an API route; a user session token or an exchanged token at the MCP server; an exchange for an audience other than the API; an exchanged token with a wider scope than its subject. Tasks 5, 7 and 9.
2. **A weak authorization request.** `plain` PKCE or none; a missing or wrong `resource`; a redirect URI that is not exactly registered (a loopback port may differ, nothing else may); an open redirect through the consent page. Tasks 3 and 4.
3. **Replay.** An authorization code used twice (the tokens it produced are revoked); a rotated refresh token presented again (the whole chain is revoked). Task 5.
4. **A revoked connection still working.** Introspection says inactive on the next call; an exchanged token whose grant was revoked is refused before it expires. Tasks 5 and 7.
5. **Reach beyond the table.** An exchanged token on a route outside the table is a 403, whatever its scope; no route reachable by an exchanged token deletes anything. Task 7. (The second round, `docs/superpowers/specs/2026-10-04-mcp-second-round-design.md` §4.3, lets an exchanged token with `dossier:delete` move rows to a trash; deleting for good stays out of reach.)
6. **Registration abuse.** More than five redirect URIs, an HTTPS URI outside the allow-list, a flood from one address, a client name built to mislead on the consent page. Tasks 3 and 6.
7. **Writing too much or the wrong thing.** 51 references in a call; an article that does not exist; an ambiguous reference next to good ones; a dossier that is not the user's. Tasks 8 and 10.
8. **The daily limit.** A `429` becomes a tool error that says when the quota renews, not a crash. Tasks 7 and 10.
9. **Secrets in logs and errors.** No token, code, secret or hash appears in a log line or an error body. Tasks 5 and 9.
10. **A deleted account.** Every OAuth row of the person goes with them, through `deleteUserAccount`. Task 2.

## Phase 1: the dossier (criterion 5)

### Task 1: The compatibility probe and the pinned versions

**Files:** none in the repository. A scratch directory outside it; the findings go into the "Results" paragraph of this task.

- [x] A minimal MCP server (one tool) on the official SDK's latest release, Streamable HTTP, stateless; first with no authentication, then with the SDK's own authorization router and an in-memory provider that auto-approves consent.
- [x] Connect Claude Code (a temporary `--mcp-config`, never `claude mcp add`, so nothing persists) and LibreLex's client library to it.
- [x] Read Anthropic's documentation for the OAuth callback address(es).
- [x] Choose the port for `apps/mcp`.
- [x] Find the cheapest existing Python call that confirms an article exists.
- **Results (2 October 2026, scratch code outside the repository; nothing in the repository or in Claude Code's configuration was changed):**
  - **SDK:** `@modelcontextprotocol/sdk@1.31.0` (released 28 September). It serves 2025-11-25 and the earlier revisions, not 2026-07-28. Pin it; bump it in its own task when it serves the newer one.
  - **Protocol, measured:** Claude Code 2.1.287 sends `MCP-Protocol-Version: 2026-07-28` first and falls back to 2025-11-25; LibreLex's library (fastmcp 3.4.7 on mcp 1.30.0) and the SDK's client use 2025-11-25. Stateless Streamable HTTP works with all three (a tool call returned through each; Claude Code needed a one-off `claude -p` call). A `GET` on the endpoint answers 405 and all three accept it.
  - **Claude's callback, verified on Anthropic's documentation:** `https://claude.ai/api/mcp/auth_callback` for the hosted apps; Claude Code uses a loopback redirect on a changing port (`localhost` or `127.0.0.1`). The documentation names no `claude.com` address. Claude Code declares a client-ID metadata document but falls back to dynamic registration when the server does not advertise one, so registration is enough for the spike.
  - **LibreLex's client, end to end against the SDK's router:** `401` → resource metadata → server metadata → `POST /register` → authorize (S256, `resource`, scopes from the metadata, including `offline_access`) → `POST /token` (form-encoded) → tool call → after the 8-second access token expired, a refresh with rotation and a second tool call. It works the same with the router mounted inside an Express 4 app.
  - **Three things the probe found that the plan now handles:** registration must make every client public (the SDK hands a secret to a client that did not ask, and the client then fails the exchange: Task 3); the client requests the authorization URL once before opening the browser, so `/oauth/authorize` must be safe to call twice (Task 3); `iss` must equal the metadata's `issuer` string exactly (Task 4).
  - **Claude Code's own sign-in could not be driven headlessly:** in print mode it reaches the two discovery documents and stops. It is done by hand in the acceptance test (Task 11).
  - **Existence check:** `fetch_act_fingerprints`, once per act, answers for every article at once and also gives the fingerprints the card anchors need (Tasks 8 and 12).
  - **Port:** 3002 for `apps/mcp`; the machine and the repository do not use it.

### Task 3: Metadata, registration and the authorization request

**Files:** create `apps/server/src/oauth/` (`config.ts`, `metadata.ts`, `registration.ts`, `authorize.ts`, `redirectUri.ts`, `hash.ts`), `apps/server/src/routes/oauth.ts`; modify `apps/server/src/app.ts` (mounted before the catch-all routers, with its own rate limits); tests under `apps/server/tests/oauth/`.

**Interfaces** (produces): `GET /.well-known/oauth-authorization-server`; `POST /oauth/register`; `GET /oauth/authorize` (validates, stores an `OAuthAuthorizationRequest` for ten minutes, redirects to the web consent page); `matchesRedirectUri(registered: string[], requested: string): boolean` implementing the exact-match-plus-free-loopback-port rule.

- [ ] Tests first: metadata fields; registration accepts loopback and allow-listed HTTPS URIs and refuses everything else, more than five URIs, and a flood; **every registered client is public** (the answer says `token_endpoint_auth_method: "none"` and has no secret, even for a client that asked for one); `authorize` refuses a missing or `plain` challenge, a missing or wrong `resource`, an unknown client and an unregistered redirect, and never redirects to an unregistered address (an error is shown, not followed); **calling `authorize` twice with the same query has no side effect beyond a stored request** and issues no code.
- [ ] Implement on the SDK's `mcpAuthRouter` with a Prisma-backed `OAuthServerProvider` (spec E10): first confirm it mounts in this server's Express 4 (the probe did), then override the registration store so it enforces the allow-list and the public-client rule. The allow-list and the canonical resource URI come from configuration.

### Task 4: The consent decision

**Files:** create `apps/server/src/oauth/consent.ts`; modify `apps/server/src/routes/oauth.ts`; tests.

**Interfaces** (produces): `GET /api/oauth/requests/:id` (what the page shows: client name, redirect host, scopes, whether the client was registered automatically); `POST /api/oauth/requests/:id/decision` `{ approve: boolean }` → `{ redirectTo }`: an approved decision creates the grant (or reuses a live one) and a 60-second single-use authorization code, and the redirect carries `code`, `state` and `iss`; a refusal redirects with `error=access_denied`.

- [ ] Tests first: only the signed-in user who opened the flow can decide; a request is decided once; an expired request is refused; the redirect is exactly the registered one; the code is bound to client, redirect, challenge and resource; `iss` in the redirect equals the metadata's `issuer` string character for character.
- [ ] Implement.

### Task 5: Tokens, refresh, revocation and introspection

**Files:** create `apps/server/src/oauth/token.ts`, `introspect.ts`, `revoke.ts`; modify the routes; tests.

**Interfaces** (produces): `POST /oauth/token` for `authorization_code` (PKCE verified, code consumed) and `refresh_token` (rotation); `POST /oauth/introspect` (callable only by the confidential client `mcp-omnilex`) → `{ active, scope, sub, client_id, aud, exp, grant }`; `POST /oauth/revoke`; `GET /api/oauth/grants` and `DELETE /api/oauth/grants/:id` for the user.

- [ ] Tests first: the full code-to-token flow; a wrong verifier; a code used twice revokes what it produced; refresh rotates and the old token, presented again, revokes the whole chain; introspection of an expired, revoked or unknown token is `active: false`; only the MCP server's credential may introspect; no response or log contains a token.
- [ ] Implement. Tokens are random, stored as hashes, 8 hours (access) and 30 days (refresh). The code, refresh and revoke handlers come from the SDK's router through the provider's exchange methods; the introspection endpoint and the token-exchange grant (Task 7) are ours, so the token route is wrapped to hand those two grants to our code. A dead refresh token answers `invalid_grant`, which Claude expects.

### Task 7: Token exchange and delegated authentication — then a security review

**Interfaces** (produces): `grant_type=urn:ietf:params:oauth:grant-type:token-exchange` on `/oauth/token`; the exchanged token's claims (spec section 5); `delegatedRoutes`: dossier read and write routes and the new norms route (Task 8); a daily quota with a weight per route and `429` with `Retry-After`; named daily counters beside the points (for now `dossier_create`, at most 10 a day through an exchanged token; Task 12 adds the card one), kept in the server because the MCP process keeps no state; `GET /api/oauth/quota` (points left, creations left, when the window renews), in the table with `dossier:read`, for `omnilex_stato_account`.

- [ ] Tests first: the exchange succeeds for `mcp-omnilex` with a live subject token and a scope within it; it fails for another client, another audience, a wider scope, an expired or revoked subject; the exchanged token passes on a table route with the right scope and fails (403) on any other route and on a route whose scope it lacks; a client's own access token is refused by the API; a revoked grant refuses an unexpired exchanged token; a user-session token still works as before; the quota counts per user and per weight and answers 429; the eleventh dossier created in a day through an exchanged token is refused, a user's own session is not limited by it; the quota route reports what is left.

## Order and sequencing

Tasks 2 to 7 are a chain on the same tables and must be done in order; 8 can run beside 6; 9 needs 7; 10 needs 8 and 9. Task 1 comes first, and the owner decides whether it may start before the graph round's first phase closes (it is scratch work outside the repository). The graph round also changes the schema: both sets of migrations are dated and ordered, and the owner approves both. Server suites run one at a time, so work on these tasks does not run in parallel with another session's server suite.

**Execution:** native is recommended over one subagent per task: the tasks share one test database and tight interfaces, and a mistake in tokens or consent is costly. A fresh reviewer runs after Task 7 and over the whole branch at the end.
